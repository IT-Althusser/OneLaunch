# OneLaunch 架构说明

OneLaunch 由 React 单页应用和 Spring Boot API 组成。后端通过 `ImagePipelineService` 顺序组织图片生产过程；模型调用、规则加载和本地图片处理分别封装。当前没有独立任务队列或数据库。

## 请求与状态

前端主要使用 `POST /api/images/set/stream` 创建五图任务。后端在虚拟线程中运行流水线，通过 `SseEmitter` 发送进度。同步接口 `POST /api/images/set` 复用同一流程，最终返回完整 JSON。

SSE 发送的是应用事件：文字画像、图片开始、图片完成、质检结果等。主网关客户端保持同步调用；后端逐个平台、逐类图片处理，不为每个角色启动独立服务。

前端的 `AppShell` 管理视图和工具实例，`usePipeline` 管理图片槽位及事件状态。生成工作台和单图工具切换时隐藏而不卸载，任务可以在应用内继续执行。这种状态只存在于当前页面，不能用于刷新后恢复任务。

## 五图处理过程

1. **整理文字资料**：有名称或卖点时生成商品画像；文本调用失败则使用原始文字。仅有参考图时跳过文字画像。
2. **描述首张参考图**：有参考图时增加一次视觉调用，提取可见商品事实，供生成、质检和修复共用。失败时记录原因并继续。
3. **选择平台与市场**：未指定平台时使用 Amazon；市场以请求中的显式值为先，否则根据平台映射。
4. **按图类生成**：顺序处理白底、场景、模特、对比、尺寸图，提示词组合商品事实、图类契约、平台和市场规则。
5. **逐图检查与修复**：按审核范围执行预检和视觉检查，必要时修复，发送该图最终质检记录。
6. **发布图片检查结果**：发送 `compliance_complete`，包含当前图片和质检列表。
7. **编排详情页**：逐个平台生成详情页，失败时使用模板，最后发送包含全部结果的 `done`。

五个图类代表输出槽位，不等于五次模型调用：本地渲染会减少调用，参考图描述、质检和修复会增加调用。

### 图片生成方式

| 图类 | 流水线处理 |
|---|---|
| 白底图 | 有参考图时先尝试像素白底化；无法得到有效白底结果时调用图片编辑模型；无参考图时可文生图 |
| 场景图 | 根据当前参考图生成使用场景；没有参考图时文生图 |
| 模特图 | 生成展示商品的人物场景，图类契约包含人物出现、着装和商品完整性要求 |
| 对比图 | 有可用参考图时优先进行整体与局部像素拼合，失败时调用模型 |
| 尺寸图 | 使用本地渲染器排版，尺寸来自提供的资料；无尺寸时显示缺失提示 |

经过质检的白底图可作为后续图类的干净参考，降低原始背景噪点传播。尺寸图优先采用通过质检的白底图，原始首张参考图仍是商品一致性的基准。

单图接口 `/api/images/single` 使用独立的文生图或图生图路径，不能把流水线的尺寸图本地排版策略等同于单图工具行为。

## 图片检查与修复

### 检查范围

`MODEL_ROUTER_QA_SCOPE=all` 为默认值，覆盖五类图片。`white` 只检查白底图，并使用专门的白底视觉检查，不包含全图检查路径的 P3 双图比对和市场规则检测。

本地预检在视觉调用前执行，尺寸图跳过该步骤；其他图类检查清晰度、重度噪点，以及适用的场景边缘和模特区域肤色比例。这些启发式规则用于筛查明显问题，不是完整的人物识别或平台审核。图片读取或解码失败时跳过本地预检，继续视觉检查。阈值见 `application.yml` 的 `quality-policy.precheck`。

全图视觉检查会组合以下信息：

- 图类质量契约与平台硬性规则。
- 市场规则中图片可见的客观要求。
- 原始商品名称、卖点和首张参考图的视觉描述。
- 原始首张参考图（代码中称 P3），用于比较商品结构、颜色、材质和固有文字。

图片与商品实物是否一致，仍取决于参考图和资料的真实性。风格偏好、看不见的经营行为和授权状态不作为图片客观违规证据。

### 修复策略

本地预检失败可直接进入修复，省去该轮视觉调用。视觉问题按严重度决定是否修复，默认阈值为“高”；缺少结构化分级时保留可修复行为。

常规修复使用当前图作为编辑基准，并带上 P3 原图；噪点类失败且已有干净白底图时，改用干净基准重绘。每轮结果先预检、再视觉检查，默认最多 2 轮。白底图仍失败时另有一次文生图重制尝试。

尺寸图失败后保留检查结果，不进入模型自动修复循环，避免重新生成尺寸文字。

`ImageQualityContract` 同时提供生成、检测和修复条款。白底生成要求与检测容差需要配合：检测提示词接受均匀干净、各通道不低于 245 的近白背景，不把轻微压缩噪点直接判为违规。

### 结果语义

`QaRecord.status` 是审核状态依据：

| 状态 | 含义 |
|---|---|
| `passed` | 完成本次检查且通过 |
| `failed` | 完成检查并发现问题 |
| `manual_review` | 视觉调用或解析未完成，需要人工复检；`passed=false` |

流水线发送最终 `qa` 结果；修复时可能再次发送同一槽位的 `image_done`。客户端按平台和图类覆盖图片与检查记录，不能把事件数量当成图片数量。

## 规则库

规则位于 `apps/server/src/main/resources/compliance-rules/`，包括 4 个平台文件与 5 个市场文件。规则使用二级标题区分“通用”和图类，条目格式为：

```markdown
## 白底图
- 【规则ID】硬性：需要生成与检测共同遵守的要求。
- 【规则ID】风格：用于生成的构图或表现建议。
```

硬性条目同时注入生成和质检，风格条目只注入生成。`GET /api/compliance-rules` 提供同一规则库的快照；规则在服务启动时加载，修改后需要重新构建并重启。

增加新的可选平台或市场还需要同步目录映射和前端选项。只新增文件不等于完成界面接入。缺少平台规则时使用通用要求并告警；缺少市场规则时不注入该市场条目。

## 模型与故障恢复

主网关的文本、图片和视觉请求使用 `/chat/completions`。图片生成和编辑使用扁平 `image` part，视觉检查使用嵌套 `image_url` part。可选编辑网关支持另一套图片编辑协议，连接信息仅由服务端配置。

商品画像失败时回退原始文字；单图生成失败时记录该图错误并继续其他图；视觉检查失败时转人工复检；详情页失败时生成模板内容。SSE 流程级异常使用 `fatal` 事件。

模型目录请求失败时，`/api/models` 返回配置中的默认模型并附带 `error`，因此目录非空不代表网关可用。

## 接口边界

`ApiController` 暴露健康检查、模型目录、规则快照、图片代理、润色、同步及 SSE 五图生成、单图生成、图片本地化、合规检测和详情页生成。请求结构与事件列表见 [API 接入指南](integration-guide.md)。

系统没有持久化任务、服务端账号鉴权或自动店铺发布能力。前端与后端是独立部署产物，部署时需要配置静态站点和 `/api` 转发，见 [运行指南](runbook.md)。
